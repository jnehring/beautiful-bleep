# Bleep Script

Status: built and working in the web board; the native app and plugins have the engine side but not yet the compiler delivery (section 17). A way to write modules, message routing, and generated patches for Beautiful Bleep in code, built on **AssemblyScript** and **TypeScript**, with the module and widget system around it. Section 17 lists what exists and where the built version differs from the design in the sections before it.

It should serve four jobs:

- **custom message routing** (notes, gates, triggers, CC between modules)
- **custom scripting** (control logic, sequencing, generative rules)
- **custom modules** (DSP written by the user)
- **complex patches**, e.g. a cell with 100 oscillators generated by a loop

## 0. Summary

- **One language family: TypeScript.** Layers 2 and 3 (control and audio) are **AssemblyScript**, a TypeScript-like language that compiles to WebAssembly. Layer 1 (patch building) is plain **TypeScript** running in a sandbox at build time. The same syntax, editor and tooling serve all three.
- **Three layers by when code runs.** Layer 1 runs once, at build time. Layer 2 runs per event and per block (32 samples). Layer 3 runs per sample. Rates are chosen by which method you write (section 3), not by annotations.
- **A restricted subset in real time.** The compiler adds a checker that rejects what the audio thread must not do: unbounded loops, recursion, allocation, extra imports.
- **One output format and sandbox.** The compiler emits WebAssembly that obeys the existing module ABI and runs in the Wasmtime sandbox the engine already has. The compiler itself is JavaScript, so it runs in the plugin and in the user's browser.
- **Share source, not binaries.** A shared script is text; the viewer's app compiles it locally.
- **One module, one editor.** A *Code* module with an editor and a Compile button. Its declared parameters, probes and buttons become real knobs, jacks and meters, and its UI uses a widget registry shared with panels.
- **Specs from source.** Decorators and doc comments produce both the machine-readable spec (the `bleep_spec_json()` shape) and the human API docs.

## 1. What exists today

Bleep Script builds on things already in the repo:

| Existing | Where | How it is used |
|---|---|---|
| Sandboxed WASM modules | `patch/engine/wasm/` (Wasmtime), ABI in [module-abi.md](../../website/content/developers/modules/module-abi.md) | The compiler's output format and sandbox |
| Preset generation in JS | `patch/presets/kit.mjs` and the `*.mjs` files | The starting point of the layer 1 API |

| Module specs | `bleep_spec_json()`, `module.json`, `doc/*.md` per module | The spec and docs pipeline (section 10) |

The WASM host measured 1.16× native speed in Wasmtime and 14× slower in the wasm3 interpreter ([`patch/wasm-host/README.md`](../../patch/wasm-host/README.md)), with these limits per module: 64 MiB memory, 100 ms per call on the audio thread, 5 s for creation, a 32 MiB file, and no file, clock or environment access. Modules are signed and distributed through the library.

## 2. The three layers

| Layer | Language | Runs | Covers | Cost model |
|---|---|---|---|---|
| **1. Patch builder** | TypeScript, in a sandbox | Once, at build time | Generated patches, 100 oscillators, custom cells, module UI layouts | Loops and functions allowed, with a fuel limit |
| **2. Control** | AssemblyScript subset | Per event and per block | Message routing, custom scripting | Bounded, no allocation |
| **3. Audio** | AssemblyScript subset | Per sample | Custom modules | Compiled, no dynamic features |

Layer 1 produces an ordinary patch: nodes and cables, checked by the existing sanitiser (`BoardSanitise.cpp`) and covered by undo. Layers 2 and 3 produce one module that appears on the board like any built-in one. Layers 2 and 3 live in the same class (section 3), so they are really one thing at two rates.

## 3. Modules: AssemblyScript

### 3.1 Shape

A module is a class. Decorators declare its interface; methods are the rates:

| Method | Rate | When it runs |
|---|---|---|
| `init()` | const | Once, when the module is created. The only place that may allocate. |
| `onNote(n)`, `onEvent(...)` and other `@on` handlers | event | At each event, at its sample offset inside the chunk |
| `block()` | block | Once per 32-sample chunk (`kChunk` in `Module.h`) |
| `sample()` | sample | Once per sample |
| `frame()` | frame | About 60 Hz, only for custom drawing (section 9.3) |

`NoteEvent` already carries a sample `offset` inside the chunk. The generated `process` splits the chunk at event offsets and runs `sample()` over each span between events, so events are sample-accurate.

### 3.2 A DSP module

```ts
import { Smoother, PeakHold, dbToLin, tanh } from "bleep/dsp";

/** A wave folder with a decaying amplitude set by each note. */
@module("Fold")
export class Fold {
  @input x: f32 = 0;
  @input notes!: NoteStream;
  @output y: f32 = 0;

  /** How hard the signal is pushed into the fold. */
  @param({ min: 0, max: 1, init: 0.2 }) drive: f32 = 0;
  @probe level: f32 = 0;

  private env: f32 = 0;
  private k = new Smoother(10 * ms);

  onNote(n: NoteEvent): void { if (n.isOn) this.env = 1; }
  block(): void { this.k.target = this.drive * 20; }
  sample(): void {
    this.y = tanh(this.x * (1 + this.k.next())) * this.env;
    this.env *= 0.9995;
  }
}
```

### 3.3 A router

```ts
@module("Router")
export class Router {
  @input notes!: NoteStream;
  @input cc1: f32 = 0;
  @output low!: NoteStream;
  @output high!: NoteStream;
  @output gate: f32 = 0;
  private step: i32 = 0;

  onNote(n: NoteEvent): void {
    if (n.pitch < 0) this.low.push(n); else this.high.push(n.transposed(12));
  }
  @on("cc1", { rising: 0.5 }) ccRise(): void { this.gate = 1; }
  @on("clock", { ppq: 24 }) tick(): void { this.step = (this.step + 1) % 8; }
}
```

The decorators and the types (`NoteStream`, `f32` for audio and control) map to Bleep's signal types (`Spec.h`). The compiler's transform (section 7) rejects a jack with a type that does not exist.

### 3.4 The subset the compiler enforces

AssemblyScript is a full language. In `onNote`, `block`, `sample`, `frame` and the `@on` handlers, the checker rejects:

- loops without a compile-time bound (`for (let i = 0; i < CHANNELS; i++)` is fine; `while (x)` is not)
- recursion, directly or through calls
- allocation: `new`, growing arrays, string concatenation, closures
- any call to something outside the allowed standard library
- `memory.grow`, `unreachable`-style tricks, and imports beyond the host's fixed stubs

`init()` may allocate, up to the memory limit. Everything the real-time methods use is set up there.

The checker computes a worst-case cost per chunk where it can, so a module over budget can be rejected at compile time and not only trapped at run time. Where it cannot (a call into the standard library whose cost is known only by annotation), the standard library carries cost annotations.

### 3.5 Standard library: `bleep/dsp`

Written in AssemblyScript, inlinable, as in Faust: biquads and shelves, smoothing, envelopes, oscillators, delay lines, peak detectors, note helpers (`transposed`, `quantize`), unit literals (`ms`, `Hz`, `dB`), `dbToLin`. Only arithmetic and trig are true intrinsics. Native Bleep modules (such as the built-in filter) are not inlinable; they are used as nodes (section 5).

## 4. Foundation

| Option | Decision |
|---|---|
| **AssemblyScript** | **Chosen.** Apache-2.0 (the repository states it; whether the compiler and standard library differ was not stated). Compiles TypeScript-like source to WebAssembly with Binaryen. The compiler has a JavaScript API and a browser build. |
| Cmajor | Rejected: dual-licensed GPLv3 or a paid commercial licence, tiered by revenue. |
| Faust | Not chosen: licence unclear (GPLv2 listed by one packager, GPL-3+ with a "FAUST exception" on some components in Debian's file, LGPL-3.0 on the FaustWasm package), no help for layer 1 or events. Possible later as an extra backend. |
| SOUL | Rejected: its own licence, plus an end-user licence, inactive since 2022. |
| Own language on Binaryen | **Fallback**, if AssemblyScript fits poorly. It would keep rate inference and a real cost bound as language features, with Binaryen for code generation. |
| Rust, Zig, C | Not suitable: native toolchains that cannot compile in the app or the browser. |
| Lua, QuickJS | Layer 1 only, and AssemblyScript plus a TypeScript sandbox already covers it. |

Why AssemblyScript: no compiler to write, a permissive licence, TypeScript syntax shared with layer 1, an existing JS compiler API with in-memory file hooks, and a transform mechanism for decorators and checks.

## 5. Layer 1: the patch builder (TypeScript)

A documented, stable successor to `kit.mjs`. A cell is built by a function; loops, functions and modules come from TypeScript.

```ts
import { cell, Oscillator, Mixer } from "bleep/patch";

export default cell("SuperSaw", { n: 100, spread: 0.2 }, (c, { n, spread }) => {
  const root = c.input("root", "pitch");
  const mix  = c.node(Mixer, { inputs: n });
  for (let i = 0; i < n; i++) {
    const osc = c.node(Oscillator, { wave: "saw", detune: (i / n - 0.5) * spread });
    c.connect(root, osc.pitch);
    c.connect(osc.out, mix.in[i]);
  }
  c.expose(mix.out, "out");
  c.expose(c.param("spread", spread), "Spread");
});
```

- `n` is an ordinary number, so the loop creates 100 real nodes. They are visible on the board, run natively, and can be inspected.
- Range binding: `c.connect(lfo.out, osc.slice(0, 8).cutoff)` connects many nodes at once.
- The same code in a `sample()` method would be a tight loop inside one module. That is cheaper per voice but uses no existing native modules and is not visible on the board.

| | Graph (nodes) | Kernel (one module) |
|---|---|---|
| Cost per voice | Higher (one node each) | Lower |
| Uses existing native modules | Yes | No |
| Inspectable on the board | Yes | No |

### 5.1 Loading other modules

`c.node(Filter, {...})` instantiates an existing module, built-in or from the library, as a **node** in the cell. Its jacks and params are typed from its machine-readable spec (section 10). A script module that has source available can also be **inlined** in another AssemblyScript module through a normal `import`. Native and compiled-only modules are nodes only: they are separate WebAssembly or native code, called once per 32-sample chunk, and cannot be called sample by sample.

A cell can expose a loaded module's params under new names and ranges:

```ts
c.expose(eq.low, `ch${i}.low`, { name: "Low", min: -15, max: 15 });
```

### 5.2 Worked example: a mixer with a configurable channel count

Graph version, reusing library modules and one small custom module (volume, mute and solo):

```ts
import { cell, EQ3, Filter, LevelMeter, Mixer as AudioMixer } from "bleep/patch";
import Gains from "./gains.dsp";        // the AssemblyScript module below

export default cell("Mixer", { channels: 8 }, (c, { channels: n }) => {
  const mixer = c.node(AudioMixer, { inputs: n });
  const solo = c.node(SoloBus, { inputs: n });         // combines every strip's solo flag

  for (let i = 0; i < n; i++) {
    const eq = c.node(EQ3, { low: 100, mid: 1000, high: 8000 });
    const lp = c.node(Filter, { mode: "lowpass", cutoff: 12000 });
    const g  = c.node(Gains);
    const m  = c.node(LevelMeter);

    c.connect(c.input(`ch${i}`, "audio"), eq.in);
    c.connect(eq.out, lp.in);
    c.connect(lp.out, g.x);
    c.connect(g.out, mixer.in[i]);
    c.connect(g.out, m.in);
    c.connect(g.soloOut, solo.in[i]);
    c.connect(solo.othersFor(i), g.othersSolo);

    c.expose(eq.low,  `ch${i}.low`);
    c.expose(eq.mid,  `ch${i}.mid`);
    c.expose(eq.high, `ch${i}.high`);
    c.expose(lp.bypass, `ch${i}.lp`);
    c.expose(g.vol,  `ch${i}.vol`);
    c.expose(g.mute, `ch${i}.mute`);
    c.expose(g.solo, `ch${i}.solo`);
    c.expose(m.level, `ch${i}.level`);
  }
  c.connect(mixer.out, c.output("main", "audio"));
});
```

```ts
// patch/script/src/gains.dsp.ts (AssemblyScript), as built in the spike
import { PeakHold, Smoother, dbToLin } from "./bleep/dsp";

@module({
  name: "Gains",
  category: "Utility/Mixing",
  colour: "#94a3b8",
  description: "Volume, mute and solo for one channel, with smoothing. Written in Bleep Script.",
})
export class Gains {
  @input({ name: "In", type: "audio" }) x: f32 = 0;
  @input({ name: "Others Solo", type: "gate" }) othersSolo: f32 = 0;
  @output({ name: "Out", type: "audio" }) out: f32 = 0;
  @output({ name: "Solo Out", type: "gate" }) soloOut: f32 = 0;

  @param({ name: "Volume", min: -60, max: 6, init: 0, unit: "dB", decimals: 1, minText: "-inf" }) vol: f32 = 0;
  @param({ name: "Mute" }) mute: bool = false;
  @param({ name: "Solo" }) solo: bool = false;

  /** The output level, for the channel's meter. */
  @probe level: f32 = 0;

  private gain: Smoother;
  private on: Smoother;
  private meter: PeakHold;
  private started: bool = false;

  constructor(sampleRate: f64) {
    this.gain = new Smoother(sampleRate, 0.010);
    this.on = new Smoother(sampleRate, 0.005);
    this.meter = new PeakHold(sampleRate, 0.3);
  }

  reset(): void { this.started = false; this.meter.reset(); }

  // block rate: once per chunk; inputs hold their first sample of the chunk
  block(): void {
    this.gain.target = this.vol <= -59.95 ? 0 : dbToLin(this.vol);
    this.on.target = this.mute || (this.othersSolo >= 0.5 && !this.solo) ? 0 : 1;
    this.soloOut = this.solo ? 1 : 0;
    if (!this.started) { this.gain.snap(); this.on.snap(); this.started = true; }
  }

  // sample rate
  sample(): void {
    this.out = this.x * this.gain.next() * this.on.next();
    this.level = this.meter.next(this.out);
  }
}
```

The all-kernel version (one AssemblyScript module with `CHANNELS` strips, filters inside) is cheaper at 8 channels and keeps solo logic in one place. It needs the channel count at compile time (`--use CHANNELS=8`, a compiler option) and a transform that expands array declarations such as `@param({ count: CHANNELS }) low` into indexed params. The Code module passes its settings as such constants.

## 6. Security of shared scripts

The model is: share source, compile locally, run sandboxed.

1. **No capabilities in the language.** The real-time subset has no file, clock, network or imports beyond the host's fixed stubs. Sample access goes through the existing `MediaService`.
2. **Bounded by construction.** The subset (3.4) removes unbounded loops, recursion and allocation from real-time code. The checker can reject a module over its cost budget at compile time.
3. **WASM sandbox as the second wall.** Memory is capped, time is limited by epoch interruption, and a trapping instance is bypassed to silence. The current audio-thread budget (100 ms) is a dropout; for script-compiled code the limit should be much closer to the chunk deadline.
4. **Layer 1 is sandboxed too.** It runs in a JS sandbox with a fuel (time) limit and memory cap, and can only call the cell-building API (no `fetch`, no storage, no DOM). Its output goes through the sanitiser, with caps on node count, cable count and size.
5. **The compiler is sandboxed.** The AssemblyScript compiler parses untrusted source. It runs in a worker (browser) or a restricted process (plugin) with time and memory limits, and reads files only through the API's `readFile` hook, which serves the script's own sources and the standard library from memory.
6. **Source is the shared artifact.** Short and readable. The viewer's app compiles it with its own compiler version, so no foreign binary is trusted. Publishing and "who made this" stay with the library's existing signing.
7. **Determinism.** WebAssembly output is bit-reproducible (the wasm-host spike matched native within about 1e-6), so a script sounds the same on every machine.
8. **UI code.** See 9.5.

## 7. Compiler and transform

The compiler is the AssemblyScript compiler (`asc`) plus a Bleep **transform**.

- **API.** `asc.main()` is called with CLI-style arguments and hooks: `readFile`/`writeFile` (so the file system is in memory), `stdout`/`stderr` (diagnostics) and `transforms`. In browsers the compiler loads through the generated `web.js`.
- **Transform hooks.** `afterParse` runs before types are known, `afterInitialize` after types resolve, and `afterCompile` can change the IR before output. The Bleep transform:
  - reads the decorators (`@module`, `@input`, `@output`, `@param`, `@probe`; later `@button`, `@on`) and generates the spec JSON (section 10);
  - expands array declarations (`count: CHANNELS`);
  - runs the subset checker and the cost bound;
  - generates the ABI exports (`bleep_create`, `bleep_process`, `bleep_spec_json`, ...), including the `NoteEvent` mapping and probe copy-out;
  - removes or stubs imports (`env.abort`, `env.seed`, ...), using `--noExportMemory` and related options, so only the allowed set remains.
- **Runtime.** `--runtime stub` or a custom minimal runtime: no garbage collector, no allocation outside `init()`. This fits the ABI and the memory cap.
- **Constants.** Module settings (like `channels`) become `--use NAME=value` constants.

**Built** ([`patch/script/transform/bleep.mjs`](../../patch/script/transform/bleep.mjs), tested in `patch/script/test/transform.test.mjs` and in a browser page):

- Reads `@module`, `@input`, `@output`, `@param` (float, integer, choice, bool) and `@probe`, and the methods `block()`, `sample()` and `reset()`.
- Generates the node type description and the entry source with all `bleep_*` exports. The entry source is added to the compilation in `afterParse` (`parser.parseFile`), so the compiler type-checks it like user code and errors read as source. Adding exports to the IR in `afterCompile` was the alternative and was not needed.
- Decorator arguments are read by a small literal parser, never evaluated: an identifier or call in a decorator is an error.
- Errors carry the file and line (`gains.dsp.ts:14: @input field 'x' must be f32, not i32`); the compiler's own errors come through `reportDiagnostic` with a source range.
- It runs unchanged in node and in a page, and the page's output is byte-identical to node's.
- `@input` and `@output`, not `@in` and `@out`: `in` is a reserved word and does not parse as a decorator name.

How the generated glue maps the ABI's buffers to the module's fields (the contract between the transform and the module author):

| Field | Holds | Set |
|---|---|---|
| `@param` | The value in its own units (dB, an integer, a choice index, a boolean) | Once per chunk, before `block()` |
| `@input` | The signal | Its first sample of the chunk in `block()`; the current sample in `sample()` |
| `@output` | What the module wrote | Read back after each `sample()` (and after `block()` for a block-rate output such as a flag) |
| `@probe` | A value for the view | Read by `bleep_live` (about ten times a second) |

A param's default is its `init` option or, if absent, the field's initial value; both given and different is an error. Not built yet: `@button`, `@on` event handlers and notes jacks, array params (`count`), `map: "exp"|"skew"` params, `@data`, TSDoc as description, the subset checker and cost bound, and `--use` constants.

### 7.1 In the browser

The pipeline is source → `asc` (JavaScript, in a worker) → module bytes → `WebAssembly.compile` → instance. A compiled `WebAssembly.Module` can be posted to the AudioWorklet, so compilation never touches the audio thread. The plugin and the web app must run the same compiler and transform version; the language and library versions are stamped on every saved script.

Caveats:

- The browser worklet's chunk is 128 frames and the engine's is 32; the cost bound is computed per engine chunk. How the web build handles this today is not verified.
- Wasmtime needs executable memory. Hosts without it fall back to wasm3, which is 14× slower, so only simple modules suit it there.

## 8. The Code module and the authoring flow

A library module, **Code**, with a panel that has:

- **Editor tab.** Source with highlighting, error markers (from the compiler and the checker) and a **Compile** button, plus a shortcut.
- **Panel tab.** The module's controls.
- **Info strip.** Status (compiled, error, bypassed), the worst-case cost per chunk, and the build settings (like `channels`).

On **Compile**:

1. The source is compiled.
2. On success, the new version is swapped in with a short crossfade. Fields whose name and type are unchanged keep their values (as Elementary Audio keeps state across graph updates).
3. On failure, the previous version keeps running and the editor shows errors with line numbers. A typo never silences the module.

Jacks and knobs do not exist until the first compile. After each compile, the declarations become the module's real spec, as for any built-in module. Cables to a jack that disappears are kept and flagged, not deleted.

| What you write | What you get |
|---|---|
| A `@module` class | A DSP, router or scripting node |
| A TypeScript `cell` | A generated cell on the board, marked read-only and replaced on each compile |

The second case needs its own result type. Preferred: a separate **Patch script** module that expands into an inner cell it owns.

**As built: the playground** ([`patch/script/playground/`](../../patch/script/playground/index.html), run it with the `script-spike` server in `.claude/launch.json` and open `/script/playground/`). It is the Code module's editor, compile flow and automatic panel as a standalone page, not yet inside the board:

- A source editor (a plain textarea with line numbers, Tab indents, Ctrl/Cmd+Enter compiles), an examples menu (Gains, Wave folder, Tremolo) and the source saved in the browser.
- **Compile** runs `asc` and the Bleep transform in the page (about 0.3 s per module). Problems are listed with line and column, click to jump; the error line is marked in the gutter. A failed compile leaves the previous version playing and its panel in place.
- On success the new module is swapped into an AudioWorklet through the Bleep browser module host, fed by a test signal (sine, saw, noise, silence). Knob values are kept for params that still exist.
- The panel is built by the board's own `BleepView` from the generated description, so the dial, toggles and choice selector are the real ones. Probes are shown as live meters, polled about twelve times a second.
- Checked in the in-app browser with all three examples, mute, a deliberate type error and switching between modules. Not covered by an automated test.

Not built: the CodeMirror editor, hot reload with a crossfade that keeps `state`, the cost display, compiling in a worker, and, above all, the board integration below.

**Decided: one Code node per script, each with its own interface.** A Code node carries its source and the interface that source declares: `node.code = { source, interface }`. The board reads the node's jacks, knobs and probes from `node.code.interface` (`typeOf` in `board-model.js` asks `BleepCode.uiSpec(node)`), so a saved patch shows its jacks and cables at once, before anything is compiled. The engine's rule that a node's interface belongs to its *type* is kept by giving every Code node and source a type of its own, `code:<node id>:<source hash>`; the type id changes with the source because the engine keeps a node's running module while the type id stays the same.

**As built in the board** (web build and the dev server; [`board-code.js`](../../patch/board/ui/board-code.js), [`board-code-worker.js`](../../patch/board/ui/board-code-worker.js)):

- **Add module → Code** (category Utility › Script) adds an empty Code node. Its view is the editor: a Compile button, an Examples menu (Gains, Wave folder, Tremolo), the source with line numbers, the problems list, probe meters, and below them the module's own knobs built by `BleepView` from the interface.
- **Compile** runs in a Worker that loads the compiler bundle (`patch/script`, `npm run bundle`, about 14.5 MB, 3 MB gzipped, loaded on first use; `build-web.sh` and `ui-server.py` serve it when it exists). The page must not run the compiler: the board seals JavaScript built-ins in the page, and the compiler assigns to one. On success the source and the interface are saved on the node in one undoable step, the module is registered with the engine, and the open view is rebuilt in place (`rebuildView`) with the new knobs. On failure the problems are listed and the previous version keeps running.
- **Loading a patch** compiles each Code node's source in the background (`BleepCode.sync`, called from `BleepWeb.setBoard`) and registers the module when it is ready, with or without audio started. Sources are compiled once per hash.
- **Cables survive** a recompile as long as the jack ids still exist, and a Code node keeps its cables and its saved interface when the compiler is not available.
- **Undo and redo** restore the source, the interface and, through the same `sync`, the running module.
- Checked in the in-app browser against a rebuilt site with the real engine and local modules: Keyboard, Oscillator, Filter, Code, Amp and Speakers; compile, live swap between Fold, Tremolo and Gains while a note was held (the engine's own probe values show which module runs), reload of the saved patch, undo, the dev server with its strict content-security policy. `patch/web/test/board-code-test.mjs` covers the pure parts. No automated end-to-end test.

**Not built:** the native app and the plugins (the engine there would need to accept a compiled module and its description for a node, the way `WasmRuntime` already runs library modules; a Code node there shows as a missing module), panel wiring to a Code node's knobs (the panel tools look knobs up by node type), CodeMirror, the cost display, and a build step for the bundle in CI. The website's content-security policy already allows WebAssembly; a policy delivered as a response header must also allow it for workers and must not block `data:` in `connect-src` (the bundle avoids that one itself).

Saving and sharing: the source is stored in the patch or preset. *Save as library module* publishes it through the library. A script shared as source is compiled by whoever opens it. Also planned: an examples dropdown, a rate-limited `console.log` in the panel, live field values on hover, and agent integration (`agent/` writes scripts and uses the compiler's errors as feedback; TypeScript-family source is a good fit for it).

## 9. User interfaces

### 9.1 What exists

A module's view is `BleepViews.register("lfo", { layout, template, afterBuild })`. Knobs come from the module spec; the view reads live values with `view.value(st, "pw")` and `st.phase`. Panels ([panels.md](panels.md)) have dial, slider, wheel, button, switch, select, keys, XY pad, meter/scope, label, section, tabs, panel-in-panel, and parts of module views.

### 9.2 The interface a module exposes

Four channels, all declared by decorators:

| Channel | Direction | Declared as | Today's equivalent |
|---|---|---|---|
| Params | UI → module, and automation | `@param` | `params[]` in the spec |
| Buttons | UI → module event | `@button` | `buttons[]` in the spec |
| Probes | module → UI, about 30 Hz | `@probe` | `st.phase` etc. |
| Data | either way, a blob | `@data` | `bleep_set_data` |

Nothing else reaches the module. A probe is a snapshot copied out on a timer, so the audio thread never waits for the UI. Arrays (e.g. 64 spectrum bins) should be allowed as a probe type.

### 9.3 Three levels of UI

1. **Automatic panel.** `@param` declarations become knobs, grouped by an optional `group` option, as the module view builds them from any spec. Most script modules stop here.
2. **Widgets bound to signals**, declared in a build-time TypeScript layout file next to the module (layer 1 again):
   ```ts
   export default layout((ui, m) => {
     ui.row(() => {
       for (let i = 0; i < m.channels; i++) ChannelStrip(ui, m, i);
       ui.column("Master", () => ui.faderMeter({ fader: m.master, meter: m.masterLevel }));
     });
   });
   ```
3. **Custom drawing.** A `frame()` method (about 60 Hz) emits drawing commands (`clear`, `line`, `rect`, `text`) that the host draws on a canvas. Same language, same sandbox, no DOM. Custom JS (like `lfo.js`) is possible but is the risky option; see 9.5.

### 9.4 A shared widget registry

A set of widgets used by both panels and module views. A widget knows how to draw and take input, but not where it sits. It sees only **bindings**:

```
widget(props, bind)
  bind.value(id)     read a number (in the param's units)
  bind.set(id, v)    write it (with gesture begin/end for undo)
  bind.stream(id)    live data: level, waveform buffer, probe value
  bind.command(id)   press a button
  bind.theme         colours
```

The host fills the bindings in: a module view from the module's params, outputs and probes; a panel from a control's `wire` list. A dial written once then works on a panel (wired to `filter.cutoff`) and in a script module's automatic view (bound to `@param drive`), as `BleepView.create(type, node, api)` already splits it.

| Widget | Exists today | Bindings |
|---|---|---|
| Dial, slider, wheel, button, switch, select, XY pad, keys, label | Panel controls; knob/toggle/select in module views | value in/out |
| Meter | Panel meter | stream in |
| Scope | Panel scope; `xy-scope` | stream in |
| **Fader** (scale marks, 0 dB detent) | Slider exists; scale is new | value in/out |
| **Waveform display** | `wave-analyzer`, `sampler` | stream or buffer in |
| Step lane, curve editor, EQ response, spectrum | Only as per-module code (sequencers, `shape-env`, `segments`, `eq`) | extraction needed |

**Composite widgets** are widgets made of widgets with their own exposed bindings, e.g. *Fader + Meter* = a fader bound to `vol` and a meter bound to a probe. The existing panel-in-panel and "parts of a module view" mechanisms are special cases.

A **cell** is separate: it contains the audio part too. A *channel strip cell* (gain module, level meter module and a panel that loads the Fader + Meter composite) can be dropped on the board with no wiring. The UI composite is for when the audio already exists elsewhere.

Existing module views mostly draw their displays with their own canvas code (92 modules, many over 300 lines), so the registry needs an extraction step. The shared parts that exist today are `BleepView.fit`, `theme`, `glow` and `loop`.

### 9.5 Security of UI code

JS from a shared script would run in the app's page and could reach storage, patches and the network. So:

- By default a script has no UI JS: automatic panel, widgets from the registry, or a draw list.
- Custom JS runs in a **sandboxed iframe** without same-origin access, a CSP that blocks all network requests, and a small message API (read params and probes, set params, draw to its own canvas, get the theme).
- It is allowed only for signed library modules, or after an explicit per-module user approval shown like a permission.

Custom JS is left out of the first release.

## 10. Specs and documentation: one source of truth

Every module, native or script, exposes the same machine-readable spec (the shape `bleep_spec_json()` produces): params, jacks, types, ranges, groups.

- **Script modules.** The transform generates the spec from decorators and types. TSDoc comments (`/** */`) on the class, each field and each method become the human text.
- **Native modules.** `module.json` plus `doc/*.md` already exist; the library merges them into the same shape.
- **One generator** builds the API reference for every module from spec plus docs: the website, the editor's autocomplete and hover text, and the compiler's type-checking of `c.node(Filter, {...})` calls.
- **The standard library** (`bleep/dsp`, `bleep/patch`) is documented by the same tool.
- **The agent** reads the same specs, so it can write correct calls without guessing.

## 11. Dependencies and sharing

- `import` for AssemblyScript and TypeScript code; library modules by pinned id, e.g. `use "bleep/filter@3"`, resolved through the library.
- A shared script records the dependencies' version and content hash (like a lock file), so a dependency cannot change underneath it.
- Opening a script whose modules are missing prompts to install them, like a missing plugin, following the library's signing and trust rules.
- A loaded module is another sandboxed module with the same limits. Loading gives a script no extra capabilities.
- `import ... as Name` avoids name clashes.

## 12. Tooling

What can be reused around AssemblyScript and TypeScript. Items marked (verified) were found in project pages; the rest are from memory and need checking in the spike.

### 12.1 Editor

| Tool | Use | Notes |
|---|---|---|
| **CodeMirror 6** (MIT) | Syntax highlighting, folding, error markers, autocomplete for the Code module | Small and embeddable. Use the TypeScript mode. First choice. |
| **Monaco** (MIT) | Full IntelliSense, hover docs and go-to-definition through the TypeScript language service | Several MB. Better editing, heavier in a plugin window. Later, only if IntelliSense proves worth it. |

- Both can show the compiler's diagnostics as markers: `asc` returns errors through its `stderr` hook, and the Bleep checker adds its own.
- The TypeScript language service needs AssemblyScript's type definitions (`i32`, `f32` and the built-in standard library). How to load them into the editor is not checked. Some TypeScript errors will be wrong for AssemblyScript and need filtering.
- Hover and autocomplete for `bleep/dsp`, `bleep/patch` and the decorators come from typings generated from the specs (section 10).

### 12.2 Compiler tooling

- **visitor-as** (verified): a library for writing AssemblyScript compiler transforms, the natural base for the Bleep transform (reading decorators, expanding arrays, enforcing the subset). It is lightly maintained (last push February 2024; a health score of 46/100 on one tracker), so test it against the current compiler early and be ready to write the visitors directly.
- **Binaryen** (what AssemblyScript compiles with): `wasm-opt` can optimize the output, and its validator is an extra safety check on imports and features.
- **Prettier and ESLint**: format-on-save and lint rules for TypeScript syntax. Custom ESLint rules deliver the subset warnings in the editor before the real compile.

### 12.3 Tests

- **as-pect** and **as-test** (verified): test frameworks for AssemblyScript. as-pect is Jest-inspired, and at least one list marks it unmaintained; as-test is newer (v0.3.5) and works with WASI or bindings.
- The Code module should first offer a small Bleep test harness instead: feed a module known input and compare its output, as the wasm-host spike did. Adopt a framework only if that falls short.

### 12.4 Documentation

- **TypeDoc** (from memory) generates API pages from TSDoc comments (`/** */`), which editor hovers also understand. It could build the human docs for the standard library and for module sources, alongside the generator in section 10.

### 12.5 Not reused

- `@assemblyscript/loader` and `as-bind`: helpers for talking to modules from JS. Bleep has its own ABI.
- WASI shims: modules deliberately get no WASI.
- Existing AssemblyScript audio code: some DSP and AudioWorklet examples probably exist but none were reviewed; reference reading only.

## 14. Phasing

1. **Spike** (decides whether this foundation holds). **Done** for a hand-written module; results in [`patch/script/README.md`](../../patch/script/README.md):
   1. Licences: AssemblyScript 0.28.20 and Binaryen are both Apache-2.0 (read from the installed packages).
   2. A `Gains` mixer channel compiles to a 10 KB `.wasm` that imports nothing (`--runtime stub --use abort=`).
   3. It passes the engine's Wasmtime host (`WasmRuntime`) and the browser module host, and matches a JS reference model within 1e-5 of the peak.
   4. The compiler and a transform run in a browser page (about 0.6 to 0.9 s for this module); transforms read decorators; output is byte-identical to node.
   5. Speed: 16 ns per sample in Wasmtime (0.08 % of a core at 48 kHz). Not compared with a native C++ build of the same code.
   Not covered: the time budget on a module that never returns, notes and events with offsets, hot reload, and a worker (the page ran on the main thread).
1b. **Transform** (decorators to node type description and `bleep_*` exports). **Done** for modules with inputs, outputs, params of all four kinds and probes; section 7 lists what is built and what is not. `Gains` is written with it and passes the same checks as the hand-written spike.
2. **Code module** with the CodeMirror editor (section 12.1), compile flow and automatic panel (section 8, UI level 1). **Playground and board integration done for the web build** (section 8); the native app and plugins, CodeMirror and panel wiring are open.
3. **Subset checker and cost bound**, then events with sample offsets (`onNote`, `@on`).
4. **Layer 1 API** (TypeScript) and the Patch script module, with sanitiser and fuel caps.
5. **Widget registry** (binding contract; move dial, meter, scope; then fader and waveform; then step lane and curve editor extraction).
6. **Spec and docs generator**; library publishing of script modules.
7. **Custom views** (draw list), later a sandboxed JS option.

## 15. Risks

- AssemblyScript is a general language with its own quirks; the subset checker and the transform are the real work, and the transform API is documented as needing deep compiler knowledge.
- The spike is one small DSP module written by hand. The transform that generates the interface and the ABI entry file from decorators, events, probes with arrays and array-style params are all unproven.
- With `--runtime stub` nothing is freed: `bleep_destroy` leaks inside the instance's own memory. Choose `--runtime minimal` or a bump allocator rewound by `bleep_reset` before shipping.
- AssemblyScript's standard library is small: no `toFixed`, so number formatting, and probably more, is ours to write.
- The module ABI may constrain how events and the 32-sample chunk are passed in; `module-abi.md` has not been checked against section 3.1.
- Unifying panels and module views under one widget contract touches both; whether `panels.js` and `bleep-view.js` share drawing code today has not been verified.
- Live data for meters and waveform displays: whether the engine can supply a buffer, not only a value, has not been verified.
- Hot reload with a crossfade, and keeping fields across compiles, need care to avoid clicks.
- Without a language-level rate system, a mistake like reading a fast value in a slow method is caught only by lints (for example, `block()` reading an `@input` audio signal), not by types.

## 16. Open questions

1. How is the cost budget per chunk defined, enforced and shown in the editor?
2. Which standard library functions are intrinsics, and which are source?
3. Which widgets are in the fixed kit at release, and which are extracted from the sequencers and envelope editors first?
4. Should the Patch script module be a separate module from Code?
5. Should a probe carry arrays, and what is the maximum size?
6. If the spike fails, do we fall back to the own language on Binaryen, or look at Faust as a backend?
7. How are array declarations such as `@param({ count: CHANNELS })` best expressed, so the checker and the editor understand them?

## 17. What is built

Everything below runs and is tested; `patch/script` has the code, `patch/script/README.md` the commands.

| Part | Where | State |
|---|---|---|
| Transform: decorators to spec JSON and ABI exports | `transform/bleep.mjs` | `@module`, `@input`, `@output`, `@param` (float, int, choice, bool; linear, `exp`, `skew` as the engine maps them), `@probe`, `@button`, `@on`; `count` for numbered jacks, params and probes; module `settings` (a count the user sets); TSDoc comments as descriptions |
| Subset checker and cost bound | `transform/subset.mjs` | Section 3.4 as written: no host imports or raw memory, no unbounded loops, recursion, allocation, closures or exceptions in real-time code; an estimate of ops per 32-sample chunk (limit 400,000, warning at 60,000), shown in the editor. The estimate is conservative: about 4 times the measured time for Gains |
| Events | `src/bleep/notes.ts`, transform glue | Notes jacks (`NoteStream`, `NoteEvent`), `@on("jack")` for note events at their sample offset, `@on("jack", { rising/falling: level })` for edges. Not built: a transport clock handler |
| Standard library | `src/bleep/dsp.ts`, `format.ts` | `Smoother`, `PeakHold`, `Biquad` (shelves, bell, low-pass), `dbToLin`, number formatting |
| Layer 1: patch scripts | `patch/` | **TypeScript or JavaScript run in QuickJS compiled to WebAssembly** (memory and time limits, no network, files, clock, DOM), checked against the board's module types, producing a cell of modules and cables. This differs from section 5, which put layer 1 in a host-language API; the script API is `cell(name, { settings }, (c, s) => ...)` with `c.add`, `c.cable`, `c.input`, `c.output`, `c.stereo`, `c.place`, in `export default cell(...)` |
| Compiler in the browser | `compiler/`, `bundle.mjs` | One 15.6 MB ES module (asc, Binaryen, the transform, the library, QuickJS, sucrase; about 3 MB gzipped), loaded in a Worker. The editor (CodeMirror 6, MIT) is a separate 471 KB bundle |
| Code node in the web board | `patch/board/ui/board-code*.js` | Section 8. Settings row, patch scripts, regeneration that keeps the user's cables, undo, panel wiring to a Code node's knobs |
| Native engine | `patch/engine/wasm/CodeNodes.*`, `Registry`, `Board`, `BoardSanitise` | A Code node keeps its cables, knob values and `code` when loaded, before anything is compiled; the module the UI compiled is registered for the node and runs in Wasmtime; a changed source is a new type. Tested in `patch/tests/code_node_test.cpp` (not a ctest: it needs the module built in `patch/script`) |
| CI | `.github/workflows/ci.yml`, `website/Dockerfile` | The script tests run in the rules job; the bundles are built before the site |

**Where the built version differs from the design above**

- Decorators are `@input` and `@output` (`in` is reserved). Array jacks use `count`, not `[n]`.
- A Code node stores `{ source, interface, settings }` on the node; the engine type is `code:<node id>:<hash of source and settings>`.
- Layer 1 is not AssemblyScript and not a host-language library: it is a sandboxed script that returns a description.
- Rates are methods, not inferred sections, and the checker enforces rules by syntax and call-graph, not by a rate type system.
- The module's `bleep_destroy` frees nothing (stub runtime); allocation happens in constructors only.

**Not built**

- The native app and plugins cannot compile a script yet: the compiler bundle is not delivered there. A dev build serves it from `patch/script/dist` (`BLEEP_UI_DEV_ROOT`); a release needs it to arrive as a library package or an embedded file (16 MB is too large for JUCE's binary data). The engine side is done and tested. Whether the native WebView can run a module Worker from its resource scheme is not verified.
- Hot reload that keeps module state across a recompile, and a crossfade.
- Widget registry, custom `frame()` views, custom JS views, `@data`, a transport clock handler, library publishing of script modules, the generated API reference.
- No browser test is automated: the board was driven by hand in the in-app browser.
